# RFC-001 — Replay Matrix

**Status**: DRAFT (v0.2)
**Authors**: <你>
**Last updated**: 2026-05-18
**Related**: lipas.replay (P2.7), lipas.tool_harness (P3.1), lipas.effect (P3.0)

## 1. Scope

This RFC defines the authoritative behavior of LIPAS replay across the four `SideEffectClass` values and the three replay modes. It governs both `LLMHarness` (already-implemented LLM-call replay) and the planned `ToolReplayer` (Phase 4). After this RFC reaches STABLE status, any change to replay behavior requires an RFC amendment.

This RFC does **not** cover:

- Persistent store backends (RFC-004, planned).
- Distributed trust under partition (Phase 6 design).
- Compensation / undo semantics across kinds (RFC-005, planned).

## 2. Why a matrix at all

LIPAS records every effect as a pair of claims (`effect_intent` + `effect_result | effect_rejected`). Replay is the operation of producing a new run that is **observationally equivalent** (formally defined in §2.5) to a recorded run, against either the same or a different store. The user-facing question — "should this tool be re-executed during replay, or substituted from tape?" — has **no single right answer**. It depends on:

1. The tool's `SideEffectClass` (declared at registration).
2. The replay mode (audit vs. development vs. live re-run).
3. Whether a recorded result exists for this call.

A matrix is the smallest correct expression of the policy. Hard-coding a single behavior (e.g. "always substitute") makes audit replay safe but blocks development workflows; hard-coding "always re-execute" makes development cheap but makes EXTERNAL_WRITE replay catastrophic.

## 2.5 Observational Equivalence

This RFC normatively defines observational equivalence as the property that replay must preserve. It is the contract that makes the matrix's choices ("substitute" vs. "re-execute") meaningful — both operations must yield equivalent observations, where "equivalent" means the following.

### 2.5.1 Definition

Let \(R\) be a recorded run producing claim sequence \(C_R\), and \(R'\) be a replay run producing claim sequence \(C_{R'}\). \(R'\) is **observationally equivalent** to \(R\) (written \(R' \equiv_{obs} R\)) iff there exists a bijection \(\phi\) between the effect-bearing claims of \(C_R\) and \(C_{R'}\) such that for every pair \((c, \phi(c))\):

1. **Tag identity**: `c.tag == φ(c).tag`, restricted to the set `{TAG_EFFECT_INTENT, TAG_EFFECT_RESULT, TAG_EFFECT_REJECTED}`.
2. **Effect lineage**: `c.effect_id == φ(c).effect_id`.
3. **Payload equality**: `c.payload == φ(c).payload`, modulo a controlled set of fields (timestamps, monotonic clocks, runtime-assigned `claim_id` and `seq`) that are exempt by §2.5.3.
4. **Causal order**: if `c1` precedes `c2` in the lineage walk of \(C_R\), then `φ(c1)` precedes `φ(c2)` in the lineage walk of \(C_{R'}\).

Claims outside the tag set above (e.g. `TAG_REPLAY_DECISION`, `TAG_RESOURCE_SPENT`) are **not** subject to equivalence — they are bookkeeping, and their presence in \(C_{R'}\) but not \(C_R\) (or vice versa) does not break equivalence.

### 2.5.2 Diagnostic Decomposition

Equivalence is the conjunction of four sub-properties. When equivalence fails, the replayer SHOULD report **which** sub-property failed, because each maps to a distinct root cause:

| Sub-property | Failure name | Diagnosed cause |
|---|---|---|
| Intent equivalence (1+2 restricted to `effect_intent`) | `IntentDrift` | Tool resolution or argument binding changed between runs. |
| Result equivalence (1+2+3 restricted to `effect_result`) | `ResultDrift` | Tool behavior changed (non-determinism, version skew, upstream state). |
| Rejection equivalence (1+2+3 restricted to `effect_rejected`) | `RejectionDrift` | Guard policy or pre-flight changed. |
| Causal equivalence (4) | `OrderDrift` | Concurrency / scheduling difference; almost always a bug in the replayer. |

These names appear in `LipasReplayError` subclass messages (§6.4) so that audit logs identify the diagnostic class without parsing free-form text.

### 2.5.3 Exempt Fields

The following payload fields are **never** required to match, and equality checks for §2.5.1(3) MUST normalize them out before comparison:

- `claim_id` — runtime-generated.
- `seq` — store-assigned ordinal.
- `wall_clock_ts`, `monotonic_ts` — captured at fold time.
- `recorded_in_session_id` — replay session is, by construction, a different session.

Any other field is in scope for equivalence. Tool-specific exemptions are forbidden in this RFC; if a tool produces output with intrinsic non-determinism (e.g. a `request_id` from a remote service), the tool's `SideEffectClass` must reflect that (typically `READ_ONLY` or stricter), and `LIVE_REROUTE` of that tool will produce `ResultDrift` by design — that is the correct outcome, not a bug.

### 2.5.4 What Equivalence Does Not Imply

Observational equivalence is a property of the **claim trace**, not of the external world. Specifically:

- Equivalence does **not** imply that external systems are in the same state. A `substitute` of an `EXTERNAL_WRITE` produces equivalence at the trace level while the external system is untouched. This is intentional and is what makes audit replay safe.
- Equivalence does **not** imply byte-equal store contents. Stores will differ in seq, timestamps, and bookkeeping claims. The bijection \(\phi\) accounts for this.
- Equivalence is **not** transitive across schema versions. If \(R\) was recorded under Claim schema v1 and \(R'\) runs under v2, equivalence is undefined (see §5.6).

## 3. Dimensions

### 3.1 SideEffectClass (existing)

Definitions reproduced here for self-containment; canonical definitions live in `lipas.tools.SideEffectClass`.

| Class | Definition | Examples |
|---|---|---|
| `PURE` | No I/O, no clock, no randomness. Output is a function of arguments. | `add(a, b)`, `format_date(d)` |
| `READ_ONLY` | Reads external state but does not modify it. Repeated calls may yield different outputs. | `http_get`, `read_file`, `db_query` |
| `IDEMPOTENT_WRITE` | Modifies external state; repeated calls with the same idempotency key are no-ops after the first. | `s3_put_object(key, body)`, `set_user_attribute(user_id, key, value)` |
| `EXTERNAL_WRITE` | Modifies external state with each call. No idempotency guarantee. | `send_email`, `charge_credit_card`, `post_tweet` |

### 3.2 Replay Mode (new)

Three modes, exposed as `ReplayMode` enum:

| Mode | Intent | Recorded result missing → |
|---|---|---|
| `STRICT_TAPE` | Audit / compliance / regulatory replay. Prove that "given exactly this input log, the system produces exactly this state." | Hard fail (`ReplayMissing`). |
| `BEST_EFFORT` | Development / debugging. Replay what is recorded, fall back to live execution where safe. | Per-class fallback (see §4). |
| `LIVE_REROUTE` | Performance / diff testing. Re-execute everything that is safe to re-execute; refuse the rest. | Per-class fallback (see §4). |

Modes are properties of the **replay session**, not the tool. A single replayer instance carries one mode for its lifetime.

### 3.3 Recording Presence (derived)

Whether the current call has a matching recorded result in the source `EffectView`. Determined by `(tool_name, arguments)` match within the lineage walk. Mismatch on either field is treated as "missing" — we do not interpolate.

### 3.4 Observability-Only Schema (new)

Some tools produce side effects that are **not observable in the domain trace** — structured logging, metric emission, distributed-trace span export. They write to the outside world, but their outputs are infrastructure, not part of the application's semantic claim trace. Treating them as `EXTERNAL_WRITE` would correctly refuse them under `LIVE_REROUTE` — but that refusal is the wrong default for a tool whose output literally cannot affect application correctness.

This RFC introduces an **orthogonal flag** at tool registration:

```python
@register_tool(
    name="emit_metric",
    side_effect_class=SideEffectClass.EXTERNAL_WRITE,
    observability_only=True,   # ← new
)
```

The flag is **orthogonal** to `SideEffectClass`, not a new class value. The semantics:

1. During replay decision (§4), an `observability_only=True` tool's `SideEffectClass` is **logically downgraded to `READ_ONLY`** for the purposes of selecting an operation. Rationale: a `READ_ONLY` row of the matrix never has a "refuse" cell, and the operation chosen never modifies application state — which is exactly the contract observability tools claim.
2. The tool's *actual* `SideEffectClass` is **preserved** in the audit trail. The `TAG_REPLAY_DECISION` claim records both the declared class and the effective (post-downgrade) class.
3. The flag is **not** inferable from a tool's name or signature. It is a deliberate assertion by the tool author that the tool's effects are non-essential to observational equivalence (§2.5). Tools that lie about this break replay correctness — this is documented as an unsafe condition, analogous to a tool lying about its `SideEffectClass`.

`observability_only=True` combined with `PURE` or `READ_ONLY` is permitted but redundant (the downgrade is a no-op or upgrade-to-self).

## 4. The Matrix

### 4.1 Recorded result present

| | `STRICT_TAPE` | `BEST_EFFORT` | `LIVE_REROUTE` |
|---|---|---|---|
| `PURE` | substitute | substitute | re-execute |
| `READ_ONLY` | substitute | substitute | re-execute |
| `IDEMPOTENT_WRITE` | substitute | substitute | re-execute¹ |
| `EXTERNAL_WRITE` | substitute | substitute | **refuse**² |

¹ Re-execution of `IDEMPOTENT_WRITE` requires the tool to produce or consume an idempotency key. If absent, downgrade to substitute and emit `LipasIdempotencyKeyMissingWarning`. (Decision Q1, §10.)

² `LIVE_REROUTE` of `EXTERNAL_WRITE` is forbidden by default. An explicit `allow_external_write=True` flag on the replayer override is required. The flag is per-session, not per-tool, and emits a one-time `LipasDangerousReplayWarning`.

For tools with `observability_only=True`, the row used is the post-downgrade row (§3.4). Specifically: an `EXTERNAL_WRITE + observability_only` tool uses the `READ_ONLY` row, so `LIVE_REROUTE` re-executes rather than refuses.

### 4.2 Recorded result absent

| | `STRICT_TAPE` | `BEST_EFFORT` | `LIVE_REROUTE` |
|---|---|---|---|
| `PURE` | fail | re-execute | re-execute |
| `READ_ONLY` | fail | re-execute | re-execute |
| `IDEMPOTENT_WRITE` | fail | re-execute¹ | re-execute¹ |
| `EXTERNAL_WRITE` | fail | **refuse** | **refuse** |

¹ Same idempotency-key caveat as §4.1.

### 4.3 Operations defined

| Operation | Behavior | Claims folded |
|---|---|---|
| `substitute` | Skip live execution. Return the recorded `output` and `usage` verbatim. | None (the original claims are already in the source store). For replay-into-fresh-store, fold a `effect_intent` and `effect_result` mirroring the originals, with a new `claim_id` and `seq` but identical `effect_id` lineage. |
| `re-execute` | Run the tool live. Fold fresh `effect_intent` + `effect_result` + `resource_spent` claims as if it were a normal run. | Full pipeline. |
| `refuse` | Synthesize an `effect_rejected` with `reason="replay:refused_external"`. The replayer raises `ReplayRefused` to the caller. | `effect_intent` + `effect_rejected`. |
| `fail` | Raise `ReplayMissing` immediately, without folding. The session is aborted. | None. |

## 5. Edge Cases

### 5.1 SideEffectClass mismatch between recorded and current

Recorded run declared `PURE`; current registration declares `EXTERNAL_WRITE`. This usually means the tool's contract changed between runs.

**Policy**: The **stricter** class wins (lattice: `PURE < READ_ONLY < IDEMPOTENT_WRITE < EXTERNAL_WRITE`). Replay decision uses the stricter class.

- **Upgrade** (recorded < current, e.g. `PURE` → `EXTERNAL_WRITE`): emit `LipasReplayClassUpgradeWarning`. Always non-fatal — the stricter behavior is the safe direction.
- **Downgrade** (recorded > current, e.g. `EXTERNAL_WRITE` → `PURE`): suspicious. Behavior controlled by an explicit `allow_class_downgrade` session flag (Decision Q2, §10):
  - `allow_class_downgrade=False` (default): raise `LipasReplayClassDowngradeError` regardless of mode. Aborts the session.
  - `allow_class_downgrade=True`: emit `LipasReplayClassDowngradeWarning` and continue, except in `STRICT_TAPE` where the abort is unconditional (audit replay must not silently cross a stricter→looser boundary).

Ordering with §3.4. When both §5.1 (class mismatch between recorded and current runs) and §3.4 (observability_only downgrade) apply to the same call, §5.1 MUST be evaluated first against the declared classes of the recorded and current runs; the resulting "current declared class" is then fed into §3.4's downgrade rule. Rationale: §5.1 is a contract-drift check between two runs and operates on each run's declared class; §3.4 is a per-run policy applied to the resolved declared class. Reversing the order would treat every observability_only tool whose declared class is stricter than READ_ONLY as a §5.1 downgrade and abort the session, which contradicts §3.4's stated semantics ("the operation chosen never modifies application state — which is exactly the contract observability tools claim").

### 5.2 Tool argument schema drift

Recorded `arguments={"x": 1, "name": "foo"}`; current tool signature only accepts `x`. The recorded call cannot be re-bound.

**Policy**:
- `substitute` operation: still legal — substitute does not re-bind, it returns recorded output.
- `re-execute` operation: `ReplayMismatch` raised (subclass of `LipasReplayFatal`, §6.4); fail the call regardless of mode.

This is the right asymmetry: substitute is a tape replay, schema drift is irrelevant; re-execute is a live call, schema drift is fatal.

### 5.3 Tool output schema drift

Recorded output shape is no longer parseable by current consumers (e.g. ReAct loop expects a string but recorded is a dict).

**Policy**: Out of scope for the replayer. The replayer faithfully returns the recorded shape. Downstream consumers are responsible for handling shape evolution. This is consistent with `ReplayCursor`'s current behavior for LLM replies.

### 5.4 Idempotency key conflicts

Recorded run used idempotency key `K`. `LIVE_REROUTE` re-executes; the external system either:
- Returns the same result (idempotency works) → fine.
- Returns `409 Conflict` (key already used, no echo) → wrapped as `effect_rejected` with `reason="replay:idempotency_conflict"`, session continues.
- Silently produces a different result (broken idempotency) → undetectable at this layer; documented as a known unsafe condition for `LIVE_REROUTE` of `IDEMPOTENT_WRITE`.

### 5.5 Partial recording (intent without result)

Source store has `effect_intent` but no `effect_result` (i.e. `EffectView.orphans`). The replayer treats this as "result missing" per §4.2.

**Policy nuance**: For `STRICT_TAPE`, an orphan in the source IS the recorded fact — replay reproduces the orphan by folding intent and immediately raising `ReplayCrashPoint`, which the session can choose to surface or treat as legitimate termination. Default: surface.

### 5.6 Replay across stores with different schema versions

Source store uses Claim schema v1; target uses v2. Out of scope for this RFC; covered by RFC-002 (Claim Schema Evolution). For now, replay across schema versions is undefined behavior.

### 5.7 View Freezing via `frozen_max_seq` (new)

A live `EffectView` is mutable: new claims may be folded by concurrent producers, or — more insidiously — by the replay session itself (each `TAG_REPLAY_DECISION` claim, every `re-execute`'s fresh effect chain). Without freezing, the view that `ToolReplayer.decide` reads from drifts as the session runs, and `(tool_name, arguments)` lookups can match against claims the replayer just folded, producing self-replay loops.

**Policy**: the replayer accepts a `frozen_max_seq: int | None` parameter. Semantics:

1. If set, all lookups against the source `EffectView` are restricted to `seq <= frozen_max_seq`. Claims beyond that seq are invisible to the replayer for the session's lifetime.
2. The default is to capture `view.max_seq()` at session construction time; passing `None` explicitly means "always read latest" and is allowed only in `BEST_EFFORT` (the only mode where reading-latest is semantically defensible).
3. `STRICT_TAPE` MUST set `frozen_max_seq` to a finite value. A `STRICT_TAPE` session with `frozen_max_seq=None` raises `ReplayConfigError` at construction.
4. `frozen_max_seq` is recorded in the first `TAG_REPLAY_DECISION` claim of the session (a session-init record), so audit consumers can reproduce the exact view slice the replayer saw.

This addresses the same class of bug that motivated the source/target store split, but at the temporal axis instead of the spatial one.

## 6. Implementation Sketch

### 6.1 New module: `lipas/replay_tools.py`

```python
class ReplayMode(StrEnum):
    STRICT_TAPE = "strict_tape"
    BEST_EFFORT = "best_effort"
    LIVE_REROUTE = "live_reroute"

@dataclass(frozen=True)
class ReplayDecision:
    operation: Literal["substitute", "re-execute", "refuse", "fail"]
    reason: str                  # for audit logging
    declared_class: SideEffectClass
    effective_class: SideEffectClass   # post §3.4 / §5.1 adjustment

class ToolReplayer:
    def __init__(
        self,
        view: EffectView,
        mode: ReplayMode = ReplayMode.STRICT_TAPE,
        *,
        allow_external_write: bool = False,
        allow_class_downgrade: bool = False,
        frozen_max_seq: int | None = ...,    # default: view.max_seq() at ctor
    ): ...

    def decide(
        self,
        tool: Tool,
        arguments: dict,
    ) -> ReplayDecision:
        """Pure function over (tool, arguments, frozen view slice, mode, flags).
        Looks up matching recorded effect; consults matrix.
        No side effects."""
        ...

    async def maybe_substitute(
        self,
        tool: Tool,
        arguments: dict,
    ) -> Optional[ToolResult]:
        """Returns substituted ToolResult or None.
        None means 'caller should proceed with live execution'."""
        ...
```

### 6.2 Integration into `ToolHarness`

Mirror the LLMHarness ↔ ReplayCursor relationship:

```python
class ToolHarness:
    def __init__(
        self,
        ...,
        tool_replayer: Optional[ToolReplayer] = None,
    ): ...

    async def call(self, tool_use_block):
        # Pre-flight order:
        #   1. resolve tool
        #   2. replay decision  ← NEW
        #   3. schema bind
        #   4. guards
        #   5. budget
        #   6. fold intent
        #   7. execute (or substitute)
        ...
```

Replay decision happens **after** tool resolution (we need the tool to know its `SideEffectClass` and `observability_only` flag) but **before** schema bind, guards, and budget. The reasoning is identical to LLMHarness's "replay short-circuits before pre-flight": the original run already passed those gates; re-evaluating against fresh state is meaningless.

### 6.3 Decision is an audit event

Every `ReplayDecision` (other than the trivial "no replayer attached") is folded as a claim into the target store under a new tag `TAG_REPLAY_DECISION`. This makes replay behavior itself auditable. Schema:

```
fields:
  effect_id:         str       # the call this decision applies to
  mode:              str       # ReplayMode value
  operation:         str       # ReplayDecision.operation
  reason:            str       # human-readable
  declared_class:    str       # SideEffectClass as declared by tool
  effective_class:   str       # post-§3.4/§5.1 adjustment
  source_seq:        int|None  # seq in source view if substituted
  frozen_max_seq:    int|None  # session-wide; only on the session-init record
```

This claim is folded into HistoryRow (Decision Q3, §10).

### 6.4 Error Hierarchy (new)

All replayer-raised exceptions are rooted at `LipasReplayError`. Two **disjoint** subtrees split fatal from recoverable conditions:

```
LipasReplayError                          (abstract base)
├── LipasReplayFatal                      (session must abort)
│   ├── ReplayMissing                     (§4.2 STRICT_TAPE)
│   ├── ReplayMismatch                    (§5.2 schema drift on re-execute)
│   ├── LipasReplayClassDowngradeError    (§5.1)
│   ├── ReplayRefused                     (§4 refuse op)
│   ├── ReplayConfigError                 (§5.7 STRICT_TAPE w/o frozen_max_seq)
│   └── ReplayCrashPoint                  (§5.5; surfaces as fatal by default)
└── LipasReplayRecoverable                (session may continue)
    └── LipasReplayWarning                (informational; not raised, emitted)
        ├── LipasReplayClassUpgradeWarning
        ├── LipasReplayClassDowngradeWarning  (§5.1, gated)
        ├── LipasIdempotencyKeyMissingWarning
        └── LipasDangerousReplayWarning
```

**Reverse constraint (normative)**: `LipasReplayRecoverable` MUST NOT be a subclass of `LipasReplayFatal`, and no class under one subtree may also appear under the other. This ensures that a handler written as

```python
try:
    ...
except LipasReplayFatal:
    abort_session()
```

cannot accidentally catch a recoverable warning, nor can `except LipasReplayRecoverable` mask a fatal abort. The `replay_tools` module asserts this constraint at import time via a class-graph walk; a violation is a packaging bug, not a runtime concern.

Diagnostic-class names from §2.5.2 (`IntentDrift`, `ResultDrift`, `RejectionDrift`, `OrderDrift`) appear as subclass tags or message prefixes on the relevant fatal exceptions, so audit consumers can filter on diagnostic without parsing free text.

### 6.5 Existing `ReplayCursor` (LLM replay) interaction

`ReplayCursor` currently silently skips TOOL_CALL nodes. This RFC formalizes the contract: **`ReplayCursor` and `ToolReplayer` are independent components consuming the same `EffectView`**. They never see each other's nodes. A typical replay session constructs both and hands them to `LLMHarness` and `ToolHarness` respectively.

`ReplayCursor` retroactively adopts the matrix as follows:
- LLM calls behave as `PURE` for matrix purposes (deterministic given input + model + system).
- Mode is implicit `STRICT_TAPE` in the current implementation; future work adds `mode` parameter for symmetry.

This is a Phase 4 cleanup task, not part of this RFC's normative content.

## 7. Shadow as Composition (worked example)

A natural request — addressed in Decision Q5 (§10) — is a fourth `SHADOW` mode: re-execute every tool call against live systems but **discard** the results, comparing them post-hoc against the recorded results to detect drift. Used for performance regression testing and behavior-equivalence monitoring.

We do **not** add SHADOW as a primitive mode. Instead, this section shows that shadow replay is achievable as a composition of existing primitives plus a thin wrapper, and argues that this composition is preferable to a primitive.

### 7.1 Construction

Shadow replay = `LIVE_REROUTE` with `allow_external_write=True` + a `ShadowToolReplayer` decorator that:

1. After every `re-execute`, fetches the matched recorded `effect_result` from the source view.
2. Compares the new result against the recorded result using §2.5.1's payload-equality rule (with §2.5.3 exempt fields).
3. On mismatch, emits a `TAG_SHADOW_DIVERGENCE` claim into the target store carrying the `ResultDrift` diagnostic; does **not** raise.
4. Returns the live result to the caller (the application observes the live behavior, the audit trail records the divergence).

```python
class ShadowToolReplayer:
    def __init__(self, inner: ToolReplayer):
        # Inner must be LIVE_REROUTE + allow_external_write=True.
        if inner.mode is not ReplayMode.LIVE_REROUTE:
            raise ValueError(...)
        if not inner.allow_external_write:
            raise ValueError(...)
        self._inner = inner

    async def maybe_substitute(self, tool, arguments):
        decision = self._inner.decide(tool, arguments)
        if decision.operation != "re-execute":
            return await self._inner.maybe_substitute(tool, arguments)
        # Fall through to live execution; intercept after.
        return None

    async def post_execute(self, tool, arguments, live_result):
        recorded = self._inner.lookup(tool, arguments)
        if recorded is None:
            return
        if not _payload_equal(live_result, recorded.payload):
            self._inner.target.fold(
                tag=TAG_SHADOW_DIVERGENCE,
                effect_id=recorded.effect_id,
                payload={"diagnostic": "ResultDrift",
                         "recorded": recorded.payload,
                         "live":     live_result.payload},
            )
```

### 7.2 Why composition is preferable

Three reasons:

1. **No new matrix cells.** A primitive SHADOW mode would require six new cells (one per `SideEffectClass × {present, absent}`). Composition reuses the `LIVE_REROUTE` cells, whose semantics are already audited.
2. **No new safety surface.** Shadow's risks (`EXTERNAL_WRITE` re-execution against production) are exactly `LIVE_REROUTE`'s risks. Forcing the user to set `allow_external_write=True` explicitly preserves the existing safety story; a primitive mode would either duplicate the flag or silently bypass it.
3. **Clean separation of concerns.** Divergence detection is a comparison concern, not a replay-decision concern. Pushing it into a wrapper keeps `ToolReplayer.decide` a pure function of (tool, arguments, view, mode), which is a property §6.1 explicitly relies on.

### 7.3 What this means for the RFC

`ShadowToolReplayer` is **not** part of this RFC. It lives in user space (or in `lipas.shadow`, a planned non-normative module). This RFC only commits to the primitives and flags that make the construction expressible — `LIVE_REROUTE`, `allow_external_write`, and a public `decide()` that wrappers can call without re-implementing.

## 8. What This RFC Does Not Decide

- **Per-tool override**: should a tool be able to declare "I am always safe to re-execute, ignore the matrix"? **Tentatively no** — overrides erode the audit trail. Reconsider if a real use case appears. (Note: this is distinct from §3.4's `observability_only`, which is a *typed* downgrade, not a free-form override.)
- **Compensation interaction**: when a `re-execute` fails during replay, should the recorded result be used as compensation? **Out of scope**; covered by RFC-005.
- **Partial replay**: replaying only a suffix of a run (skip first N effects, replay rest live). **Out of scope**; would require RFC amendment.
- **Cross-tenant replay**: replaying a recorded run under a different identity / authorization context. **Out of scope**; security review required.

## 10. Decisions Landed

(All five v0.1 open questions resolved. Reversal requires an RFC amendment.)

1. **§4.1 `IDEMPOTENT_WRITE` + `LIVE_REROUTE` without idempotency key**: **downgrade to substitute with `LipasIdempotencyKeyMissingWarning`**. Rationale: refuse would block the most common dev workflow (re-running an agent against a fixture set); the warning is sufficient because the downgrade is observable in the audit trail.

2. **§5.1 SideEffectClass downgrade**: **abort by default; opt-in with `allow_class_downgrade=True`**. The flag is per-session, mirrors `allow_external_write`, and never overrides `STRICT_TAPE`'s unconditional abort. Rationale: a recorded `EXTERNAL_WRITE` becoming a current `PURE` is almost always a refactor mistake; making the abort opt-out forces the developer to acknowledge the boundary crossing.

3. **§6.3 audit tag location**: **HistoryRow** for now. A future "ReplayRow" with its own invariants (e.g. "no decision claim without a matching `effect_intent` in the same session") is reasonable but out of scope until a second invariant emerges.

4. **Default `ReplayMode`**: **`STRICT_TAPE`**. Rationale: safer default; developers who want `BEST_EFFORT` are choosing convenience and should say so explicitly. Aligns with the project's broader "fail closed" stance.

5. **SHADOW mode**: **rejected as a primitive; supported as composition** (§7). Rationale stated in §7.2.
