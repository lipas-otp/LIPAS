# A4 v0.1 — RFC-003: Capability Sharing Semantics

> **Unimplemented proposal — not a current contract.** LIPAS supports durable
> Team handoffs, but not cross-Team capability delegation, attenuation, or a
> distributed capability ledger. These remain explicitly outside the current
> runtime boundary.

**Status**: UNIMPLEMENTED PROPOSAL (2026-05)
**Scope**: capability data model; grant / use / refund / expire / revoke lifecycle; attenuation rules across agent boundaries; replay determinism for capability state
**Related**: A1 (replay equivalence), A2 (capabilities are claims and obey schema evolution), A3 (capability fold strategy obeys purity contract)

## 0. Caveat on this version

A4 is being drafted ahead of multi-agent examples in tree. `ex06_capability_budget` exercises single-agent capability bookkeeping, but no shipped example crosses an agent boundary. This means §4 and §5 are guided by design intent rather than observed pressure, and v0.1 should be read as a **structural skeleton**: the data model and determinism story (§3, §6) are stable; the attenuation model (§5) is the most likely site of revision once `ex07` (a supervisor delegating to a sub-agent) lands.

This caveat is structural, not hedging. The alternative — defer A4 entirely until `ex07` — was considered and explicitly rejected; the choice is to write the skeleton now to **constrain `ex07`'s design** rather than the other way round. That ordering is recorded here as deliberate.

## 1. Scope

**In scope**:

- Capability as a first-class claim type with stable identity.
- Lifecycle: grant, use (quota consumption), refund (on failure / compensation), expire (logical-clock-bounded), revoke (parent withdraws).
- Sharing across agent boundaries: how a parent's grant produces a child's capability and how usage propagates.
- Replay determinism for capability state under A1.

**Out of scope**:

- Multi-process / distributed capability ledgers; no consensus protocol.
- Cryptographic capabilities (macaroons, signed tokens). Capabilities are trusted within the LIPAS runtime; the audit story is the log, not unforgeability.
- Cross-store capability migration. A capability granted in store \(S_1\) has no meaning in store \(S_2\).
- Non-quota capabilities (e.g. "read-only on resource X"). v0.1 covers quota-typed capabilities only; predicate-typed capabilities are §7 future work.

## 2. Why

Three concrete pressures, each of which would otherwise force ad-hoc local solutions:

1. **Budget enforcement during fold.** `ex06` already needs a deterministic answer to "did this tool call exceed budget?" The current implementation peeks at a `BeliefContext` field; this works in single-agent but does not generalize when a sub-agent has a sub-budget.
2. **Sub-agent delegation.** The supervisor pattern (`ex03`), in its full form, hands part of its budget to a sub-agent. Without explicit attenuation rules, "how much of the parent's budget the child consumed" is ambiguous, and replay equivalence cannot be argued.
3. **Tool-failure refunds.** When a tool call fails before doing real work, the budget should be refunded. Whether the refund is a separate claim or a mutation of the original use claim has direct replay consequences. This must be specified before `ex06`'s retry policy is wired.

Each has a "do something local" workaround that papers over the absence of A4. The cost of papering is that within two iterations the local solutions diverge, and reconciling them after the fact is strictly harder than specifying the contract now.

## 3. Capability Data Model

### 3.1 Capability as a claim stream

A capability is **not** a separate runtime object. It is a stream of claims, identified by a stable `cap_id`. The claim types are:

- `cap_grant` — capability is created (issued by parent or by system root).
- `cap_use` — quota is consumed against the capability.
- `cap_refund` — quota is returned (on tool failure or compensation).
- `cap_revoke` — capability is withdrawn (no further uses permitted).
- `cap_expire` — capability is marked expired (optional emission; see §4.3).

The current state of a capability is the fold of its claim stream. Reasons for this design:

- It is the only choice consistent with A1 §2.5: any state that affects replay must be derivable from the log.
- It gives capability state the same auditability as everything else, for free.
- It composes with A2 (capability claims have `schema_version`) and A3 (the fold strategy for capability is pure integer arithmetic — trivially compliant).

### 3.2 The grant claim

```python
@dataclass(frozen=True)
class CapGrant:
    cap_id:       str            # globally unique, deterministically generated (§3.4)
    parent_id:    str | None     # None iff granted by system root
    holder:       str            # agent id that holds this capability
    quota_kind:   str            # "tool_calls", "usd_cents", "tokens", ...
    quota_amount: int            # smallest meaningful unit; integer for replay safety
    expires_at:   int | None     # logical clock tick, NOT wall time (§4.3)
    grant_ts:     int            # logical clock at issue time
```

**Quota is integer.** Floats are forbidden in capability accounting because float addition is not associative across reorderings, and replay must be bit-exact. Use cents for currency, token-units for LLM tokens, etc.

**`expires_at` is a logical tick, not wall time.** A3 forbids wall-clock reads in strategies; capability evaluation happens during fold, so capability expiration must be checkable without consulting the clock. Logical ticks are derived from claim sequence position; see §4.3.

### 3.3 The use / refund / revoke / expire claims

```python
@dataclass(frozen=True)
class CapUse:
    cap_id: str
    amount: int          # > 0
    reason: str          # free-text, audit-only

@dataclass(frozen=True)
class CapRefund:
    cap_id:    str
    amount:    int       # > 0; refund credits the original cap, not the parent
    refund_of: str       # claim_id of the corresponding CapUse, for traceability
    reason:    str

@dataclass(frozen=True)
class CapRevoke:
    cap_id: str
    reason: str          # audit-only

@dataclass(frozen=True)
class CapExpire:
    cap_id: str          # optional; expiration is implicit in the strategy (§4.3)
```

### 3.4 Stable `cap_id` derivation

```
cap_id = sha256(parent_id || holder || quota_kind || grant_ts || nonce_seq)[:16]
```

where `nonce_seq` is a per-parent monotonic counter (count of `cap_grant` claims previously issued by this parent). Properties:

- The same parent issuing the same grant in two replay runs produces the same `cap_id` — required by A1.
- No external randomness — A3-compliant.
- Collision probability is negligible at LIPAS scale; if cardinality grows, the truncation length is the lever to adjust. The choice of 16 bytes is enough at \(10^9\) capabilities to keep collision probability well below \(2^{-30}\).

## 4. Lifecycle

### 4.1 Use, and the over-spend rule

A `CapUse` claim is **always recorded**, even if it would over-spend. The fold strategy decides whether the use is **honored** or **rejected**, and emits a derived `cap_use_outcome` claim accordingly:

\[
\texttt{cap\_use\_outcome} \in \{\texttt{honored},\ \texttt{rejected\_overspend},\ \texttt{rejected\_revoked},\ \texttt{rejected\_expired}\}
\]

Rationale: the alternative — silently dropping over-spend uses at the strategy layer — is replay-hostile, because the trace then depends on which over-spends happened and were swallowed. By recording every use and tagging the outcome, the log is a complete record and replay reproduces outcomes deterministically.

The strategy in pseudocode:

```python
def cap_fold(state, claim):
    if isinstance(claim, CapUse):
        if state.revoked:                       return state, "rejected_revoked"
        if state.expired_at(claim.tick):        return state, "rejected_expired"
        if claim.amount > state.remaining:      return state, "rejected_overspend"
        return state.minus(claim.amount), "honored"
    # ... cap_refund, cap_revoke similarly
```

This is the entire production logic. It is trivially A3-pure.

### 4.2 Refunds

A refund is an explicit, separate claim. It does not mutate the original use claim. Constraints:

- A refund's `amount` must be ≤ the corresponding `CapUse.amount`. Over-refunds are rejected with `cap_refund_outcome = "rejected_overrefund"`.
- A refund is permitted even if the capability is revoked or expired. Reason: refunds correct historical accounting; whether the capability is still usable is a separate question.
- Refunds always credit back to `cap_id`, never to the parent. Cascading refunds (child refund → parent re-credit) are §7 future work; they require a transactional model v0.1 does not specify.

### 4.3 Expiration on logical clock

`expires_at` is a logical tick. The fold strategy treats a capability as expired when the **current claim's** logical tick exceeds `expires_at`, **not** when wall time passes. Concretely:

- Each claim has a stable position index in the log.
- Expiration is checked against this index, not against `time.time()`.
- A capability "expires" in replay at exactly the same point as it expired originally — a wall-time scheme cannot promise this.

A `cap_expire` claim is **not required** to be emitted explicitly; expiration is implicit in the strategy. It may be optionally emitted at the first post-expiry use, for audit clarity. v0.1 leaves this optional and §8.1 records the consistency question.

### 4.4 Revocation

A `cap_revoke` claim immediately marks the capability as revoked. All subsequent `CapUse` claims against it are rejected. Revocation is permanent in v0.1 — there is no "un-revoke." Reasons:

- Reversible revocation creates a third state (revoked-but-restorable) and a transition the strategy must reason about.
- The use case for un-revoke is unclear; if it surfaces, the cleaner pattern is to issue a fresh grant with a new `cap_id`, not restore the old one.

## 5. Sharing Semantics: the Attenuation Model

This is the section most likely to be revised after `ex07`.

### 5.1 The pure-attenuation rule

When agent \(A\) holds capability \(\mathrm{cap}_A\) (quota \(Q\) remaining) and grants to child agent \(B\):

- The grant produces a new capability \(\mathrm{cap}_B\) with its own `cap_id`, distinct from \(\mathrm{cap}_A\).
- \(\mathrm{cap}_B\)'s initial quota is some \(q \le Q\).
- **The parent's quota is not deducted at grant time.** Both \(\mathrm{cap}_A\) and \(\mathrm{cap}_B\) independently track usage.
- However, \(\mathrm{cap}_B\)'s usage is *also* charged against \(\mathrm{cap}_A\) via a derived `CapUse` claim on \(\mathrm{cap}_A\). See §5.2.

### 5.2 Charge-through

When \(\mathrm{cap}_B\) records a `CapUse` of amount \(m\), the strategy emits a derived `CapUse` of amount \(m\) on \(\mathrm{cap}_A\). This is the attenuation enforcement mechanism:

- If \(\mathrm{cap}_A\) has insufficient remaining, the use is rejected on \(\mathrm{cap}_A\), which cascades to a rejection on \(\mathrm{cap}_B\).
- Honored uses deduct from both balances simultaneously.
- Refunds cascade similarly: a refund on \(\mathrm{cap}_B\) emits a derived refund on \(\mathrm{cap}_A\).

A child can never collectively spend more than the parent's quota allowed, regardless of how the child structures its own sub-grants. The parent is the source of truth; child caps are accounting overlays.

The alternative — deduct at grant time, treat the sub-cap as an independent budget — was rejected because it makes parent revocation strictly more complex (the parent would have to "reclaim" outstanding child quotas, which is not a deterministic operation on a stream of claims).

### 5.3 Multi-level chains

Charge-through composes: if \(A \to B \to C\), a use on \(C\) charges \(B\), which charges \(A\). The chain is walked via `parent_id` on each `CapGrant`. Termination is guaranteed because grants form a strict tree — a child's parent is fixed at grant time and never re-parented.

Cycles are forbidden by construction: `parent_id` must reference a `cap_id` whose `grant_ts` is strictly less than the current claim's logical tick.

### 5.4 What this rules out

- A child holding capability the parent does not — impossible by §5.1's \(q \le Q\).
- A child outliving parent revocation — `cap_revoke` on \(\mathrm{cap}_A\) implies all descendants are revoked. (Strategy detail: revocation propagates **lazily**, evaluated on next use of any descendant cap. This avoids a global sweep.)
- A child consuming after parent expiration — same lazy-propagation rule.

## 6. Replay & Determinism

A1's replay equivalence is preserved iff:

1. All capability operations are claims — ✓ by §3.1.
2. All `cap_id`s are deterministic — ✓ by §3.4.
3. The fold strategy is A3-pure — ✓ by §4.1, integer arithmetic.
4. Expiration is logical-clock-based — ✓ by §4.3.
5. The attenuation tree is determined by `parent_id`, set at grant time, never mutated — ✓ by §5.3.

The only externally visible nondeterminism risk is the **ordering of derived claims**: a `CapUse` on \(B\) emits a derived `CapUse` on \(A\), and in a chain \(A \to B \to C\) the `CapUse` on \(C\) emits derived uses on both \(B\) and \(A\). Resolution: derived claims are emitted in a fixed order — leaf-first, walking strictly toward the root. The fold strategy specifies this; replay reproduces the same emission order.

## 7. Edge Cases / Non-Goals

- **Non-quota capabilities** (e.g. "may access path /foo"). v0.1 is integer-quota only. Predicate caps are a future RFC; the data model in §3 is intentionally factored so that predicate caps can slot in alongside, not replace, quota caps.
- **Cascading refunds across the chain.** §4.2 explicitly defers this. Current rule: refunds credit only the cap they were issued against. The asymmetric implication — a child's refund does *not* re-credit the parent's charge-through — is intentional but uncomfortable, and may be revisited.
- **Cap reissuance after revoke.** §4.4 forbids un-revoke. The pattern "issue a new cap with the same shape" is the supported workaround.
- **Adversarial sub-agents.** A sub-agent that lies about its own usage is bounded by the parent's charge-through (§5.2) — it cannot collectively spend more than the parent allowed. *Which* sub-agent overspent within the parent's budget is a downstream auditing concern, not a determinism concern.
- **Root grants.** The system itself issues topmost capabilities with `parent_id = None`. There is no synthetic "system cap"; root grants are simply unparented. Whether to add a synthetic system root for uniformity is §8.2.

## 8. Open Questions for Review

1. **Implicit vs. explicit `cap_expire` emission.** §4.3 leaves emission optional. Consistency argues for always-emit (audit clarity); minimalism argues for never-emit (it's derivable). **Lean**: never-emit, with an `is_expired(cap_id, at_tick)` helper. Audit tooling reconstructs from the strategy.
2. **Synthetic system-root cap.** Per §7. Adds uniformity (every cap has a parent); adds noise (every store gets one extra root grant). **Lean**: skip — `parent_id = None` is fine, and the strategy already handles it.
3. **Cascading refunds.** §4.2. The asymmetry is real and may bite once retry policy lands. **Open**, lean toward "specify in v0.2 once retry has surfaced concrete cases."
4. **Attenuation model itself.** §5 is the biggest revision risk after `ex07`. Pure-attenuation + charge-through is the simplest replay-safe option I can see, but `ex07` may expose use cases (parallel sub-agents, fan-out tasks) where the model's overhead exceeds its value. **Open by design** — flagged in §0.
5. **Quota-kind compatibility checks.** Should the strategy reject a grant where `cap_B.quota_kind != cap_A.quota_kind`? **Lean**: yes — mixed-unit charge-through is meaningless. Currently unenforced; should be added before `ex07`.
6. **Schema versioning of capability claims.** A2 applies trivially: `cap_grant`, `cap_use`, etc. carry `schema_version`. No special treatment needed; called out only because the interaction is otherwise easy to overlook.
