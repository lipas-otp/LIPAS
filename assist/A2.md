# A2 v0.1 — RFC-002: Claim Schema Evolution Protocol

**Status**: DRAFT (v0.1)
**Scope**: claim-level versioning, upcaster registry, read/write paths across versions, replay across versions
**Related**: A1 (RFC-001 — replay matrix), A3 (fold determinism contract), B1 (SQLite backend)
**Length**: ~3 pages

## 0. Why Now

Claims are currently in-memory dataclasses. Once they land in a persistent store (B1, imminent) with even a few weeks of trace history, three pressures arrive simultaneously:

1. **New tags are added** — supervisor work alone introduces `goal_blocked`, `tactic_fired`, etc.
2. **Existing tags grow fields** — `tool_result` will gain `attempt_index` once retry policy is real.
3. **Field semantics shift** — what `confidence: float` meant in week 1 is rarely what it means in week 12.

Without a versioning protocol, the first time a field's meaning shifts, every historical claim in the store becomes silently mis-interpreted. Replay against pre-shift logs returns plausible-looking but wrong results — the worst possible failure mode for a system whose value proposition is auditability.

A2 specifies the minimum protocol that lets the schema move while keeping the log immutable and replay sound.

## 1. Scope

- **In**: per-tag schema versioning, upcaster registry, read-time upcasting, write-time canonical version, replay across versions, deprecation lifecycle.
- **Out**: cross-tag migrations (split one tag into two, merge two into one). Recorded in §7 as future work.
- **Out**: branching schemas (two live versions of the same tag in the same store). Strict linear evolution per tag is assumed.
- **Out**: strategy registry evolution. Strategies are code, not data; they evolve by code review.
- **Out**: BeliefContext schema evolution. Treated as a special case in §6.

## 2. Versioning Model

### 2.1 Version is per-tag, not global

Each claim carries:

```python
@dataclass(frozen=True)
class Claim:
    tag: str            # e.g. "tool_result"
    schema_version: int # monotonically increasing per tag, starts at 1
    fields: dict        # tag-specific payload
    # ... existing kind / priority / source / ts
```

The version is **per-tag** rather than a single global integer. Reasons:

- A global version forces every tag to bump in lockstep; in practice 90% of evolution is one tag at a time. Lockstep coupling makes upcaster registries quadratic in the number of tag-pairs.
- Per-tag versioning lets `goal_blocked` march from v1 to v5 while `tool_result` stays at v2. Each tag's upcaster chain is linear and short.
- Per-tag also means a deprecated tag can be frozen at its terminal version without affecting active tags.

**Initial version is 1.** There is no v0; v0 would be the un-versioned alpha state, and we explicitly bump every existing tag to v1 at the moment A2 lands. No "implicit v0" semantics — claims either have a version or they predate A2 (rejected at read time with a one-time backfill migration; see §5.1).

### 2.2 Canonical version

For each tag, the registry tracks a **canonical version**, which is the version that current code understands. Writes always emit at canonical. Reads always upcast to canonical. Downstream code (strategies, supervisors, replayers) only ever sees canonical-version claims.

```
write path:   Claim(tag, canonical_version, fields_at_canonical) → log
read path:    log row (tag, v_old, fields_at_v_old) → upcast chain → Claim at canonical
```

The log itself is **immutable**. A claim written at v2 stays as v2 on disk forever, even after the canonical advances to v5. Upcasting is a read-time operation. This is non-negotiable: if upcasting were write-time (rewriting historical rows), replay would no longer reproduce the original byte sequence, and the claim_id-based hashing in A1 §3 would break.

## 3. Upcaster Registry

### 3.1 Signature and registration

```python
Upcaster = Callable[[dict], dict]
# Input:  fields dict at version N
# Output: fields dict at version N+1

def register_upcaster(tag: str, from_version: int) -> Callable[[Upcaster], Upcaster]:
    """Decorator: register a function as the v{N} → v{N+1} upcaster for `tag`."""
    ...
```

Usage:

```python
@register_upcaster(tag="tool_result", from_version=2)
def _tool_result_v2_to_v3(fields: dict) -> dict:
    """v3 introduces `attempt_index` (default 0 for legacy claims)."""
    return {**fields, "attempt_index": 0}
```

**Each upcaster bumps version by exactly one.** Multi-step upcasts are composed at read time by the registry, not written by hand. Reasons:

- Composition is associative; a chain `v1 → v2 → v3 → v4` is unambiguous.
- A direct `v1 → v4` upcaster duplicates logic and creates a maintenance hazard (the day you add v5, you have to also write v1 → v5, v2 → v5, ...).

### 3.2 Upcaster purity

Upcasters MUST be pure functions of their input dict. The same A3 contract applies: no clock, no environment, no I/O. This is critical because the same on-disk row, read at two different times, must yield the same canonical claim.

Concretely, the test tool from A3 §4 is extended with an `upcaster_purity_check` mode that runs each registered upcaster against a fixture suite under `deterministic_fold()`. (Note: the context manager is named `deterministic_fold` for historical reasons; A2 reuses it. If a rename is desired, that is an A3.v0.2 amendment.)

### 3.3 Registry invariants

The registry enforces at registration time:

- For tag `T` with canonical version `K`, upcasters MUST exist for every `n → n+1` where `1 ≤ n < K`. No gaps.
- A version `K` is canonical iff there is no upcaster from `K`.
- Registering `from_version=K` (where K is canonical) advances canonical to `K+1` atomically.

Violations raise `LipasSchemaRegistryError` at import time, not at first use. This is deliberate: a misconfigured registry should fail before any claim is read, not produce a silent gap discovered three months later in a rare replay.

## 4. Evolution Classes

A2 partitions schema changes into three classes. The class determines whether an upcaster is sufficient or whether external action is required.

### 4.1 Additive (forward-compatible)

A new optional field with a default value.

- **Upcaster**: trivial, fills the default.
- **Operational impact**: none. Old claims are upcast on read; new claims contain the field.
- **Example**: `tool_result.attempt_index` introduced in §3.1 above.

### 4.2 Field rename / type change

A field is renamed, retyped, or restructured.

- **Upcaster**: performs the transformation. May be lossy in the v_new → v_old direction (no downcaster is required — see §6.1).
- **Operational impact**: any code reading `fields["old_name"]` must be updated to `fields["new_name"]` in the same commit that bumps the canonical. CI gates this via grep-level lints (recorded in §7).
- **Example**: `confidence: float (0..1)` becomes `confidence: Literal["low", "medium", "high"]`. Upcaster bins the float.

### 4.3 Semantics change at fixed structure

Same field name, same type, different meaning.

- **Upcaster**: may be the identity function, but **MUST still be registered** to mark the version boundary. The registration itself is the semantic flag.
- **Operational impact**: every consumer of the field must be reviewed in the bump commit. There is no mechanical check possible — review discipline is the only line of defense.
- **Example**: `priority: int` shifts from "lower is more urgent" to "higher is more urgent." Upcaster inverts the value at the boundary.

This class is the most dangerous and the least mechanically catchable. §7 logs an open question on whether to require a `# A2-bump-rationale: ...` annotation at the upcaster registration site as a forced reviewer prompt.

## 5. Operational Implications

### 5.1 The pre-A2 backfill

When A2 lands, every existing claim in any persistent store predates the protocol and has no `schema_version`. The migration is a one-shot script:

1. Read all rows from the store.
2. Tag each with `schema_version = 1` (the implicit pre-A2 baseline).
3. Write back to a new column `schema_version INTEGER NOT NULL`.

After backfill, the store enforces `schema_version IS NOT NULL` as a constraint. Any subsequent claim without a version is rejected at write time.

This migration runs **once per store** and is not part of the normal upcaster path. It is not registered as an upcaster, because there is no v0 → v1 transformation — v0 simply did not exist as a versioning concept.

### 5.2 Replay across versions

A1 §2.5 defines replay equivalence on canonical-version claims. Concretely, the replayer:

1. Reads the original log; each row is upcast to canonical at read time.
2. Re-runs strategies against the upcast claims.
3. Compares post-fold state against the original post-fold state, **also after upcasting the original to canonical**.

This means a trace recorded at canonical=v2 can be replayed under canonical=v5, provided upcasters v2→v3→v4→v5 exist and are pure. **This is the central operational guarantee of A2**: history remains replayable across schema evolution.

The contrapositive: if a tag evolves without an upcaster (registry gap), every historical claim of that tag becomes unreadable. The §3.3 import-time check is what prevents this from happening silently.

### 5.3 Snapshots and caches

B1 considers an optional `merged` snapshot table for performance. If snapshots are introduced, they MUST carry a `schema_version_snapshot` per tag and be invalidated when any tag's canonical advances. The simpler alternative — drop the snapshot, refold from log — is recommended in B1 §3 and remains the default.

### 5.4 Deprecation

A tag is deprecated by:

1. Marking it `deprecated=True` in the registry, with an optional `deprecated_in_version` and a free-text rationale.
2. Continuing to register upcasters as needed (history must remain readable).
3. Emitting a warning at write time if any code path produces a claim with the deprecated tag.

A deprecated tag is **never removed** from the registry while any store could contain rows with it. Removing the tag would break read of historical logs. This is a permanent commitment; §7 records the question of whether stores can opt into a "purge after timestamp T" archival mode.

## 6. Edge Cases / Non-Goals

### 6.1 No downcasters

A2 deliberately does not support v_new → v_old transformation. A claim at canonical v5 cannot be presented as v2 to a v2-era reader. Reasons:

- Old code is not allowed to run against new logs in lipas's operational model — the runtime always upgrades to current canonical. Mixed-version readers do not exist.
- Downcasters double the registry surface area for no benefit.
- Most semantic changes (§4.3) are inherently non-invertible.

### 6.2 Cross-tag migrations

Splitting `tool_call` into `tool_intent + tool_invocation`, or merging two tags, cannot be expressed as a per-tag upcaster. A2 v0.1 declares this out of scope; in practice it requires a higher-order transformer that operates on claim sequences, not single claims. Recorded in §7.

### 6.3 BeliefContext schema

BeliefContext is not a claim and does not flow through the upcaster registry. Its evolution is governed by the same principles (versioning, read-time upcasting) but as a separate, narrower mechanism — a BeliefContext is a single object per store, not a stream. v0.1 leaves this as a stub; the alpha BeliefContext is small enough that ad-hoc evolution is tolerable for now.

### 6.4 Concurrent canonical advance

If two developers simultaneously bump canonical for the same tag, they create a registry conflict at merge time. This is a code-review / source-control concern, not a runtime concern, and is handled by treating the upcaster registry as ordinary source code.

## 7. Open Questions for Review

1. **Forced rationale annotation on §4.3 (semantics-change) bumps.** Should the registry refuse to register an identity upcaster without a non-empty `rationale` argument? **Lean**: yes — the failure mode of unannotated semantic shifts is the worst case in §4, and the cost of the annotation is one line.
2. **Lints for §4.2 (rename) bumps.** Is a grep-level CI check sufficient, or should we go to AST-level field-access tracking? **Lean**: grep first, AST when grep produces a false negative in practice. (Same "correctness over cleverness" principle as B1.)
3. **Cross-tag migrations.** Is the "claim-sequence transformer" abstraction worth specifying preemptively, or strictly YAGNI until the first split-tag refactor surfaces? **Lean**: YAGNI. Document the constraint, design when it bites.
4. **Upcaster purity test integration with A3.** A3's `deterministic_fold()` is currently named for the fold path. A2 reuses it for upcasters. Either rename to `deterministic_pure_zone()` (broader) or accept the historical name. **Lean**: accept the name — renaming costs more than it saves at v0.1.
5. **Deprecated-tag archival.** Should stores support an opt-in "purge tag T from rows older than timestamp ts" mode? This permanently breaks replay of those rows but bounds storage. **Open**: probably yes for production, but specifying it now is premature; it interacts with retention policy that doesn't exist yet.
6. **Pre-A2 backfill atomicity.** §5.1 assumes a one-shot script. For larger stores (Postgres at >10⁷ rows), this is non-trivial. **Lean**: alpha scale doesn't need it; specify when Postgres backend lands.
